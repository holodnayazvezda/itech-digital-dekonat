# Как подготовить доказательства по четырём критериям

Источник формулировок — [страница VibeCoding](https://challenge.mgimo.ai/cabinet/nominations/vibe-coding), раздел «Критерии оценки» в [снимке](../sources/task/vibe-coding.txt). Максимум 40 баллов; по 10 за критерий. Нет опубликованной формулы частичных баллов или гарантированного набора функций для 10/10. Ниже — наш план убедительной демонстрации.

| Критерий | Что оценивается по заданию | Какие доказательства готовить | Что может ослабить работу |
| --- | --- | --- | --- |
| Проработанность идеи | Проблема студентов, реальные задачи, полнота ядра, сильные идеи, меняющие привычный опыт | Один понятный конфликт студенческого дня, связанные сценарии, обоснование разделов, честно обозначенные гипотезы, сквозная демонстрация | Набор разрозненных экранов, выдуманные интервью, красивый главный экран с недоделанными заявками |
| Масштаб использования нейротехнологий | Осмысленность ИИ в разработке, постановка задач, структура контекста агентов, работа с ошибками, дизайн/контент, описание процесса | Реальные задачи и диалоги по этапам; промежуточные снимки; пример ошибки ИИ, её обнаружения и исправления; роли человека и инструментов | Перечень популярных моделей без подтверждения использования; восстановленные задним числом «диалоги»; ИИ-чат без пользы |
| Имплементация | Рабочий URL, сценарии без ошибок, сохранение, телефон, защита, синтетика, тестовые аккаунты, прочие требования | Два студента в независимых сессиях, реальная сохранённая заявка, проверки доступа к чужим записям, чистый запуск, мобильный прогон, проверка хостинга | Состояние только в браузере, кнопки без действия, пропажа заявки, секреты в JS, недоступный из РФ сервис |
| Качество | Цельный стиль, навигация, быстрота поиска, пустые/ошибочные/загрузочные состояния, скорость и доступность | Экран 360 px и десктоп, фокус клавиатуры, контраст, понятные подписи и ошибки, доступный статус обновления, быстрая загрузка | Декоративная перегрузка, мелкий текст, непонятные названия, отсутствие видимых состояний, данные «для красоты» без согласованности |

## Выводы для приоритизации

**Сначала закрыть ядро и проверяемую надёжность.** Новая функция не компенсирует отсутствие входа, мобильной подачи заявки или разделения данных. Все четыре критерия имеют одинаковый потолок; не стоит отдавать большую часть времени только визуальному оформлению.

**Дополнительная идея должна усиливать связность.** Например, перенос занятия может быть заметен в расписании, породить уведомление и предложить понятное действие. Это усиливает уже обязательные разделы. Новый раздел, не связанный с повседневной задачей, добавляет стоимость, но не гарантирует преимущества.

**Описание процесса — часть конкурентного результата.** Его нельзя полноценно восстановить после завершения кода: ранние варианты и ошибки нужно фиксировать во время работы. Содержание PDF здесь отличается от описания агента в прежнем треке.

**Масштаб ИИ не равен количеству сервисов.** В тексте нет минимального количества инструментов, моделей, субагентов или запросов. Полезная цепочка постановка → результат → проверка → исправление лучше доказывает вклад ИИ, чем неподтверждённый список названий.

## Наш приоритет работ

| Приоритет | Работы | Условие завершения |
| --- | --- | --- |
| P0 | Вход, два аккаунта, серверное разграничение, хранение, пять модулей, 360 px, доступный URL | Пройден весь базовый путь, включая отрицательную проверку доступа |
| P1 | Связность задач, цельный дизайн, пограничные состояния, доказательства процесса | Понятен ежедневный смысл продукта и видны реальные итерации разработки |
| P2 | Одна сильная дополнительная возможность | Польза показана в том же сценарии; P0/P1 не страдают |
| Сдача | Описание со скриншотами, исходники, доступы; по возможности видео | Каждый материал открывается у жюри и соответствует финальной версии |

Это приоритеты разработки, а не официальные весовые коэффициенты.
