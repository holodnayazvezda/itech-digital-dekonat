# Доказательства процесса работы с ИИ

Собирать с первого изменения продукта. Это материалы для обязательного описания процесса. ИИ-ассистент Codex прочитал задание в Firefox, сопоставил его с регламентом, изучил университетские кабинеты и проработал предлагаемый сценарий. Текущий результат — документ с концепцией.

## Зафиксированный эпизод проектирования 20.11.2026

Автор попросил «закрыть все из них и более того сделать какие-то киллер-фичи» и поставил вопрос об отдельном мобильном приложении. Codex сверил четыре критерия с исходным текстом, использовал результаты просмотра ИТМО и сравнения 15 вузов, разобрал объём для адаптивного сайта, установки веб-версии и отдельного приложения. Первоначальное продуктовое предложение — экран «Сегодня» с обнаружением пересечения после переноса и переходом к обращению. По каждому критерию предложено наблюдаемое доказательство. Пользователь задал цель и варианты объёма, ассистент подготовил сценарий и обоснование. [Результат эпизода](ANALYSIS.md#предлагаемая-концепция)

Автор уточнил, что подтверждение переноса относится к составлению расписания, и привёл бронирование помещения как пример задачи студента. В актуальной концепции студент получает уведомление о переносе, выбирает комнату между парами, пользуется зачёткой и заказывает документы. Пример бронирования через ИСУ и my.itmo подтверждён [публичной страницей библиотеки](https://lib.itmo.ru/services).

| Поле записи | Что сохранить |
| --- | --- |
| Задача | Какой сценарий или требование улучшаем; ссылка на R-ID |
| Инструмент | Фактическая IDE/ассистент/модель/сервис, если версия известна |
| Вход | Реальный ключевой промпт, приложенные ограничения и файлы |
| Решение | Краткое обоснование выбранного подхода и существенная альтернатива; без восстановления скрытых рассуждений модели |
| Результат | Изменённые файлы/коммит, снимок макета или работающего экрана |
| Проверка | Что проверили, какой результат получили |
| Ошибка и исправление | Реальный неудачный вариант, причина отклонения и следующий запрос |
| Человек | Что выбрал, уточнил, проверил или сделал вручную |

Не нужно записывать каждое нажатие. Нужны показательные этапы: декомпозиция, архитектура/данные/права, первый рабочий путь, визуальная итерация, мобильная версия, обнаруженная ошибка, публикация и приёмка.

Для каждой используемой библиотеки, шрифта, иконки, изображения и генератора фиксировать источник и лицензию. Если инструмент не использовали, не добавлять в список ради масштаба. Не утверждать работу субагентов, интервью или нагрузочные тесты, если их не было.

## Для финального описания

Выбрать небольшое число содержательных эпизодов: постановка → первый результат → проверка → исправление. Привязать их к функциям и снимкам. Отдельно показать финальные экраны и простую схему входа/хранения/прав. Не подменять описание процесса руководством пользователя. ## 20 ноября · React, Python API и проверка Swagger

По запросу участника клиент перенесён на React с Vite, а API — в отдельный Python-пакет FastAPI. Сохранены маршруты кабинета и совместимость с прежней SQLite. В Figma добавлены четыре варианта окна выгрузки и связаны 24 кнопки календаря. В рабочем приложении период, состав и формат файла выбираются независимо от вида расписания.

На временных базах проверены 30 форм, уточнение и решение по обращению, изоляция файлов и переписки, конкуренция за место, экран брони на 360 и 1440 px и получение месячного CSV из недельного вида. В Swagger UI проверен путь от входа через Authorize до защищённого GET. Отдельно запущены статическая сборка и API в парольном режиме. Проверка настоящего старта выявила несовпадение длины scrypt-хеша между генератором аккаунтов и проверкой конфигурации. После исправления добавлен тест запуска с файлом аккаунтов. Итог — 8 серверных и 5 клиентских модульных проверок, сборка и браузерные сценарии прошли. Источник воспроизводимых проверок — `solution/server/tests/` и `solution/test/`.
