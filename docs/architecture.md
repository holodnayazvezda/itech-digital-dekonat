# Архитектура цифрового деканата iTech

## Решение и границы

Проект — модульный монолит: один браузерный клиент и один Python API с постоянным хранилищем. Расписание, заявления, переписка, проживание и бронирование используют общих пользователей и требуют согласованных транзакций. Поэтому отдельные микросервисы, распределённые очереди и дополнительные базы здесь не нужны. Разделение проводится внутри приложения, по ответственности и функциональным областям.

HTTP-контракты, внешний вид и схема существующей базы при архитектурном переносе сохраняются. Идентификаторы JWT, ключи хранилища и существующие пользовательские данные не переименовываются вместе с модулями.

## Сервер

```text
server/
  main.py                 стабильная точка входа ASGI
  web.py                  API и собранный клиент из client/dist
  api/
    bootstrap.py          жизненный цикл, middleware, ошибки, Swagger
    router.py             регистрация маршрутов и связей адаптеров
    routes/               HTTP-контроллеры по функциональным областям
    streaming.py          NDJSON и завершение потока при отключении клиента
  application/            сценарии и правила выполнения операций
  assistant/              диалоги Тинки, инструменты, агент и названия чатов
  contracts/              схемы входных/выходных данных Pydantic
  security/               проверка сессий, прав и паролей
  infrastructure/
    persistence/          SQLCipher, схема, соединения и транзакции
    notifications/        доставка Web Push
    security/             шифрование и обновление сетевых паролей
    ai/                   HTTP-клиент внешней модели
  core/                   пути ресурсов, часы, ошибки, лимиты, контракты эффектов
  cli/                    управление аккаунтами и stdio MCP
  assets/, static/        серверные данные, PDF-шрифт, локальный Swagger
  tests/                  проверки API, хранения, интеграций и границ
```

Основное направление вызова: **HTTP-контроллер → прикладной сценарий → хранилище или интеграция**. `api/router.py` связывает адаптеры, `api/bootstrap.py` собирает FastAPI. `server/main.py` только экспортирует `app`: запуск `uvicorn server.main:app` остаётся прежним.

`application/requests.py` отвечает за заявления и брони; `teaching.py` — изменения занятий; `academics.py` — выбор дисциплин; `communication.py` — переписку и уведомления; `office.py` — задачи деканата; `profile.py` — аватар и сетевой пароль; `session.py` — отзыв сессии; `cabinet.py` — персональный снимок кабинета. Навигация, поиск, проживание и правила спортивных записей также выделены в свои модули.

Сервисы не создают HTTP-ответы и не импортируют FastAPI или маршруты. Ожидаемая ошибка представлена `ApplicationError`; API переводит её в прежний JSON `{error: ...}` с нужным статусом. Контракты Pydantic общие для интерфейса приложения, их повторные копии для каждого слоя не создаются.

Хранилище использует явный SQL, а не ORM. Транзакционные сценарии работают с соединением через `connect(write=True)`: прикладной сервис определяет границу операции, инфраструктурный контекст выполняет commit или rollback. Часть SQL находится непосредственно в сценариях; это осознанная модель transaction script, а не заявление о полной изоляции SQL через абстрактные репозитории. Простые общие операции записи/чтения вынесены в persistence. Схема и шифрование отделены от прикладных правил.

### Заявка, решение и уведомление

1. API проверяет JWT, входную схему и доступ к операции.
2. Прикладной сервис проверяет владельца, статус, занятость или доступность места.
3. Изменение заявки и запись уведомления проходят в одной транзакции.
4. После успешного выхода из транзакции планируется Web Push. Для таких эффектов предусмотрен контракт `TaskScheduler`, который реализует HTTP-адаптер через `BackgroundTasks`.
5. Открытый браузер получает изменение через SSE; API-снимок остаётся источником истины.

Права проверяются на сервере. Скрытая карточка интерфейса не заменяет авторизацию. Шифрование базы, хеширование паролей, изоляция владельцев и проверка повторных операций сохраняются.

### Тинки

`assistant/` содержит построение ответа, историю и вызовы инструментов. Клиент модели расположен в `infrastructure/ai/provider.py`; HTTP-маршруты чата и MCP — в `api/routes/`. NDJSON и его заголовки находятся в `api/streaming.py`. Отключение вкладки не должно обрывать завершение уже принятого хода. Ключ провайдера передаётся через окружение или защищённый файл и не входит в клиент.

## Клиент

Клиент использует **React**, Preact Signals и Vite. Vue и Vue Router удалены из зависимостей. Для текущего набора экранов используется небольшой адаптер стандартного History API: он сохраняет URL, параметры, историю браузера и восстановление вложенных экранов. Его преобразования проверяются отдельно от компонентов.

```text
client/src/
  app/
    main.jsx                 запуск React
    CampusShell.jsx          загрузка, восстановление и граница ошибок
    App.jsx                  сборка контроллера и представления
    useCabinetController.jsx координация разделов и переходов кабинета
    CabinetWorkspace.jsx     компоновка основных экранов
    CabinetDialogs.jsx       компоновка диалогов
    config.js                названия разделов и демонстрационные роли
    layout/, sections/       межраздельная компоновка
  features/
    auth/, settings/         вход, жизненный цикл сессии и оформление
    schedule/, study/        занятия, оценки, план и элективы
    documents/, booking/     формы, заявки и бронирования
    communication/           личные и групповые сообщения
    notifications/           входящие уведомления
    profile/, wifi/          профиль и сетевые реквизиты
    navigation/, search/     карта и локальный поиск
    assistant/               интерфейс Тинки и применение действий
    finance/, housing/       выплаты и проживание
    office/, people/, sports/, catalog/
  shared/
    api/                     транспорт, сеанс и идентификаторы запросов
    domain/                  общие справочники и чистые алгоритмы
    ui/                      общие элементы, загрузчики и адаптивная навигация
    state/                   контракт контекста кабинета
    platform/                Service Worker и браузерные уведомления
    routing/                 URL-контракт и адаптер истории
    styles/                  общие стили, палитра и оформление
```

**Зависимости направлены от `app` к `features` и `shared`.** Общие модули не импортируют функциональные разделы или оболочку. Функциональные разделы не импортируют `app`. Компоновка, связывающая несколько разделов, располагается в `app/sections`, а не внутри одного из соседних разделов.

Компонент отвечает за отображение и локальное взаимодействие. `actions.js` раздела содержит операции с явно переданными зависимостями: API, выбранные значения и переходы. Он не читает скрытый глобальный экземпляр приложения. `useSession` управляет подключением и очисткой доставки, `useAppearance` — темой, `useCabinetClock` — серверным и демонстрационным временем. Рендер диалогов и содержимое отдельных панелей разделены.

`useCabinetController` остаётся координатором общих состояний кабинета и переходов между разделами. Это один общий контекст на текущий кабинет, не отдельное глобальное хранилище для каждой страницы. Локальное состояние карты, формы, календаря и чата остаётся у соответствующих компонентов. Полученные от сервера права и данные не подменяются состоянием контекста.

`shared/api/campus-client.js` хранит сеанс, выполняет авторизованные запросы и применяет серверные снимки. В `sessionStorage` находится JWT текущей вкладки, в `localStorage` — предпочтение оформления. Данные разных пользователей разделяет API. Поисковая модель выполняется в Worker, браузерные эффекты уведомлений выделены в `shared/platform`.

## Данные и ресурсы

- `client/public/` — публичные изображения, карта, манифест и Service Worker; `client/dist/` — результат сборки.
- `client/src/shared/domain/` — общие алгоритмы и исходные демонстрационные справочники клиента.
- `client/scripts/sync-rooms.js` и `sync-directory.js` обновляют каталог и копии данных в `server/assets/`. API не читает JavaScript-исходники клиента.
- `server/core/paths.py` задаёт пути ресурсов относительно установленного проекта, а не текущей рабочей папки.
- База, ключи и секреты остаются вне Git. Инфраструктурные настройки действующего сервера также не хранятся в репозитории.
- Figma и её экспорт расположены в `design/`. Архитектурный перенос не изменяет дизайн экранов.

## Как добавлять функциональность

1. Определить сценарий, владельца данных и проверку прав.
2. Добавить контракт запроса/ответа, прикладной сервис и HTTP-маршрут. Зарегистрировать маршрут в `api/router.py`.
3. Сохранение провести через явную транзакцию; уведомление отправлять после commit. Не обращаться к HTTP-контроллеру из сервиса.
4. На клиенте добавить компонент и действия в подходящий `features/<раздел>`. В `app` менять только композицию и переходы.
5. Общую логику переносить в `shared` только при реальном использовании несколькими разделами; общий модуль не должен импортировать конкретный раздел.
6. Обновить адреса, прямые ссылки, схемы Swagger и проверки нужного сценария.

## Проверки архитектуры и поведения

- `client/test/architecture.test.js` проверяет направления импортов.
- `client/test/navigation-contract.test.js` проверяет URL, параметры, родительские экраны и базовый путь.
- `server/tests/test_architecture.py` не допускает HTTP-фреймворк в прикладных сервисах и импорт API в инфраструктуру.
- При переносе выполняются сборка, модульные проверки, серверные тесты и браузерные сценарии входа, прямых ссылок, форм, PDF, профиля и полноэкранных карточек на компьютере и телефоне.

Команды запуска и проверки находятся в [общем README](../README.md). Архитектурные проверки дополняют функциональные, а не заменяют их.
